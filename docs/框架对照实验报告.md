# 框架对照实验报告

> 结构化输出机制的三种拿法 · 112 条黄金集 · 同一模型 · 2×2 因子设计
> 项目：Agent 控制台（LLM Agent 全链路）
> 日期：2026-10-18 ｜ 对应提交：`881d1dc`

---

## 一句话结论

**LangChain 在正确性上是零损耗的** —— 同机制、同 prompt 下，它和手写 `client.chat.completions.create(tools=...)` 在 112 条样本上**逐条判定完全一致（b=0 c=0）**，在另造的 57 条未见样本上**同样完全一致**。

所有分数差异都来自 **prompt 与机制的匹配度**，不来自“用不用框架”。而这种“匹配”是**数据集特定**的：B2 在 112 条上比 B1 高 2 条，换到 57 条上反而低 3 条（见第 8 节）。

---

## 1. 为什么要做这个实验

项目的 `llm_router.route()` 一直是手写的：把工具说明写进 prompt，要求模型输出 JSON，再用 `json.loads` 解析。

这套做法能跑满分（112 条 100%），但有两个说不清的疑点：

1. **它是"模拟"还是"正规做法"？** 业界主流是 function calling（`tools=` 参数），我们没用。
2. **换成正规做法或换用框架，会不会掉分？** 如果掉，掉在哪一层？

于是设计了这个实验：**只重写 `route()` 这一层**，其余全部不动。

---

## 2. 实验设计：2×2 因子 + 基线

实验要拆两个变量，而不是一个：

- **变量一：机制** —— 结构化输出从哪来（prompt 里约定 vs 服务端 schema）
- **变量二：prompt** —— 提示词是 JSON 语境的，还是机制中立的

A 组（现有主线）是"手写 client + JSON 语境 prompt"这个组合，正好落在一个格子上：

|  | JSON 语境 prompt | 机制中立 prompt |
|---|---|---|
| **手写 client** | **A**（主线，100%） | —— 不存在 |
| **原生 `tools=`** | **B1** | **B2** |
| **LangChain `bind_tools`** | **C1** | **C2** |

这样每一对差值都有明确含义：

| 对比 | 差值是 | 回答什么问题 |
|---|---|---|
| A → B1 | 照抄现有 prompt 换机制 | 换机制的**移植成本** |
| B1 → B2 | prompt 从 JSON 语境改中立 | prompt **配平**能救回多少 |
| **B1 → C1** | 同机制同 prompt，只换框架 | **LangChain 值不值得用** |
| C1 → C2 | 框架内重做一次配平 | 配平效应能否**复现** |

### 控制变量做了什么

- **同一模型**：DeepSeek（`deepseek-flash`），`temperature=0`，`max_tokens=800`，关闭思考模式
- **同一份工具说明**：`TOOLS_SCHEMA` 10 个工具，2303 字符
- **同一批样本**：112 条黄金集，涵盖 10 个工具 + 闲聊
- **同一套评分**：`judge / summarize / group_rows` 全部从 `run_eval.py` **导入**，不复制——口径一旦分叉，对照就白做了
- **prompt 一字不差**：C1/C2 的 prompt 是 `from router_fc import SYSTEM_PROMPT` 直接**引入同一个对象**，不是复制粘贴。`run_compare.check_prompt_sync()` 用**身份比较**（`is`，不是 `==`）断言这一点，漂移就中止

## 3. 结果

### 3.1 总分

| 组 | 分流命中 | 完整命中 | 参数命中 |
|---|---|---|---|
| A_手写 | 100.00% | **100.00%** | 27/27 |
| B1_照搬 prompt | 99.11% | 97.32% | 27/27 |
| B2_配平 prompt | 99.11% | **99.11%** | 27/27 |
| C1_lc 照搬 | 99.11% | 97.32% | 27/27 |
| C2_lc 配平 | 99.11% | 98.21% | 26/27 |

三层指标口径：
- **分流命中** = `type` 判对（command / chat / answer）
- **完整命中** = 分流 **且** 工具名都对
- **参数命中** = 参数值与标准答案一致（分母 27，只有带标准参数的样本进分母）

### 3.2 核心发现：B1 ≡ C1，逐条一致

`B1 vs C1`：**b=0, c=0**——112 条里没有任何一条两边判得不一样。

> 注：`compare_result.json` 里这一对记的 `p=1.0`，那是"b+c=0 时的占位值"，不是"检验算出来 p 恰好等于 1"。真正的含义是**两组判定完全等同，卡方检验无从谈起**，比"p 很大"强得多。这里不要混着说。

不只统计上相等，我还逐条比了 `got_type / got_tool / args_hit` 三元组：

```
三元组(got_type/got_tool/args_hit)全同: True
判定不同的条数: 0
```

连**错的地方都一样**。现场例子（`记一下明天下午三点开会`）：

```
A_手写          -> command / add_todo / {'text': '明天下午三点开会'}
B1_原生tools    -> command / add_memo / {'text': '明天下午三点开会'}
C1_langchain    -> command / add_memo / {'text': '明天下午三点开会'}
```

B1 和 C1 都错判成 `add_memo`，而且都在同一个参数上错。这不是"分数巧合相等"，是**行为等价**。

**这意味着一件事**：换框架不引入任何正确性风险。选不选 LangChain，应该由工程因素决定（依赖体积、可读性、可维护性），而不是由准确率决定。

### 3.3 McNemar 配对检验全表

配对单位 = "分流 + 工具"都判对。b = 前者对后者错，c = 前者错后者对。

| 对比 | b | c | χ² | p | 判读 |
|---|---|---|---|---|---|
| A vs B1 | 3 | 0 | 1.33 | 0.248 | 无显著差异 |
| A vs B2 | 1 | 0 | 0.00 | 1.000 | 无显著差异 |
| A vs C1 | 3 | 0 | 1.33 | 0.248 | 无显著差异 |
| A vs C2 | 2 | 0 | 0.50 | 0.480 | 无显著差异 |
| B1 vs B2 | 0 | 2 | 0.50 | 0.480 | 无显著差异 |
| **B1 vs C1** | **0** | **0** | — | — | **完全一致** || B1 vs C2 | 1 | 2 | 0.00 | 1.000 | 无显著差异 |
| B2 vs C1 | 2 | 0 | 0.50 | 0.480 | 无显著差异 |
| B2 vs C2 | 1 | 0 | 0.00 | 1.000 | 无显著差异 |
| C1 vs C2 | 1 | 2 | 0.00 | 1.000 | 无显著差异 |

**p 值怎么读**（大白话）：拿 A vs B1 的 p=0.248 来说——**假如两套方法其实一样好，光凭运气也能看到"差 3 条"这个局面的概率是 24.8%**。四分之一的概率不算小，所以不能说"B1 比 A 差"，只能说"这 3 条的差距还不足以排除运气"。

## 4. 三个值得单独说的发现

### 4.1 缺口只有 3 条，但这 3 条集中在同一个方向

B1 相对 A 掉 3 条，**全部**是"该记待办却记成了备忘"，或"该闲聊却去记了"：

| 输入 | 期望 | A | B1 |
|---|---|---|---|
| 记一下明天下午三点开会 | add_todo | ✅ | ❌ add_memo |
| 记一下明天出门前把快递取了 | add_todo | ✅ | ❌ add_memo |
| 那个，我女朋友的生日是三月十二号 | chat | ✅ | ❌ add_memo |

方向高度一致：**都在往 `add_memo` 偏**。

原因不是随机的。A 组的 prompt 里有 13 个"输出：{...}"格式的例子，这些例子同时承担了两件事——教格式，**和教边界**（什么时候算 add_todo、什么时候算 chat）。B 组换到 tools 通道后，例子必须删掉（见 4.2），边界知识就丢了。

### 4.2 例子在 tools 模式下会"毒化"输出

这是过程中最反直觉的一条。B 组最初直接照抄 A 组 prompt，结果 delete 类样本 **0/18**：

```
tool_calls = None
content    = '{"type":"command","tool":"delete_todo","args":{"lineno":2}}'
```

模型**看懂了**（内容完全正确），但它选择了用**文本**表达这个决定，而不是填 `tool_calls`。原因就是 prompt 里那 13 个"输出：{...}"的例子：**模型会优先模仿例子的形式，而不是服从指令**。

删掉例子后 18/18 全对。

**"例子 > 指令"** 是这个项目反复踩到的头号坑（多轮对话里也踩过）。而 tools 模式下模型看不到示例，只能靠文字说清边界——这就是为什么 B 组要单独重写 prompt，也是为什么 B 组会掉那 3 条。

### 4.3 prompt 配平不是单调的：修好 2 条，又弄坏 1 条

B2 的目标是把 A 组的规则"翻译"成不依赖 JSON 的说法，信息量不变。结果：

- `B1 → B2`：b=0 c=2（**修好**开会、快递 → 完整命中 97.32% → 99.11%）
- `C1 → C2`：b=1 c=2（**修好** 2 条，但**弄坏** 1 条 → 98.21%，参数 27→26）

坏掉的那条：

```
帮我完成待办里的第4条  →  list_todos（应 complete_todo）
```

> 口径说明：这条在 C2 上是错的，在 B2 上是对的（B2 当天 27/27）。按第 8 节的漂移说明，这是**同一个 prompt 两次执行的结果差异**，不能当成"LangChain 把参数能力弄坏了"。它在这里的作用，是说明"翻译时删掉工具名会让提示变弱"这个机制——原句在 B1 的 prompt 里是 `要连着给两次 complete_todo`。

根因在翻译过程里：B1 原话是「要连着给两次 **complete_todo**」——**句中直接提到了工具名**，这是强提示。B2 我译成「连着调两次完成待办」，把工具名换成了中文，提示被稀释，模型不敢直接办，先去查了一下。

> **这是本轮最重要的方法论发现**：去 JSON 化的时候，会**连带删掉那些"看起来像格式、其实承载语义"的片段**。"tool 填 add_memo"表面在讲 JSON 字段，实际在告诉模型"这种情况用这个工具"。删掉 = 删掉一批弱示例。
>
> **prompt 与机制的耦合不只在输出格式这一层，还在"怎么描述工具"这一层。**

同类现象还有一条：B2 去掉例子后，原本靠例子承载的 `酱油用完了 → add_memo` 这类边界没了，我新写的"要去做 → add_todo"规则反而把它带偏。

### 4.4 一条 prompt 修不掉的边界

`那个，我女朋友的生日是三月十二号` 在 **B1 / B2 / C1 / C2 四组全错**，都判成 `add_memo`。

我甚至试过把原句直接抄进 B2 的 prompt 当反例（**这是数据污染，已删除**），**仍然判错**。

结论很硬：**function calling 的"要动手"倾向强于 JSON mode**，这个边界不是 prompt 能修的。A 组能判对，靠的是例子里 `今天真是累坏了` / `我这两天记性不太行` 这类 chat 样本日积月累形成的"没让我做事 = chat"模式——那是示例的效力，不是规则的效力。

> ⚠️ 同时也说明：**继续针对这 112 条调 prompt 已经没意义了**，那是在对着测试集调参。要验证"能不能修"，得换一份没见过的验证集。

## 5. 原生 function calling 的隐性代价：答话通道断了一条

这是实验中途发现的，不在原计划里，但很重要。

`route()` 在 B 组只认 `tool_calls`。那么"**工具执行完了、要跟用户说句话**"这一格怎么走？

A 组是靠输出格式解决的：`type='answer'` + `text='已经帮你记下啦…'`。

B 组没有这个槽位。实测输入 `[工具结果]: 已记下备忘录：房间密码是1234`：

| 组 | 结果 |
|---|---|
| A_手写 | `type='answer'`，`text='已经帮你记下啦：房间密码是1234。'` ✅ |
| B1 | `content='{"category":"answer",...,"text":"已经帮你把房间密码 1234 记到备忘录里了。"}'`，`tool_calls=[]` → 判成 `chat`，`text=None` ❌ |
| C1 | 同上 ❌（C1 用 B1 那份 prompt） |
| **C2** | `text='好的，房间密码 1234 已经记进备忘录了。需要的时候随时问我。'` ✅ |

**模型明明答对了**，但那句话落在 `content` 里，而 `route()` 只读 `tool_calls`，一个字符都没接住。

而且同一个 prompt 两次调用，`content` 的键名会漂：`{"type":"chat"...}` 和 `{"category":"chat"...}`——**因为没有 schema 约束它**。

### 根因

原生 function calling 的 schema **只覆盖"调工具"那一条路**（`name` + `arguments` 两个槽，写错会 400）；"不调工具、直接说句话"这条路的 `content` 是**裸地**，没有任何约束。

结构上，这条路只能有两个出口：

```
        ┌─ tool_calls 非空 → 调工具（有 schema 兜着）
模型 ───┤
        └─ tool_calls 为空 → content（无 schema）
```

标准做法是**第二次请求**：把工具结果作为 `role='tool'` + `tool_call_id` 喂回去，模型再说。

### 一条 prompt 就能修好，但这条路上没有代码

C 组加了一格就通了：

```python
return RouterDecision(type='chat', tool=None, args={}, text=res.content or None)
```

换成机制中立的 prompt（C2），`content` 就是一句真正的人话；用 JSON 语境的 prompt（C1），它就是那个没人解析的 JSON 串。

**于是这条链就闭环了**：JSON 化是**prompt 逼出来的**，不是机制缺陷。C2 证明同一个机制、同一份代码，只换 prompt 就能说人话。

### ⚠️ 这个断口，现有评测一条都考不到

112 条单轮**不喂** `[工具结果]`；多轮 25 条的 history 里也**不含**这个输入。

所以 99.11% / 97.32% 这些数字，是"**这题没出**"的分，不是"考过没扣分"。

这一条要如实写进局限里。

## 6. 反面对照：A 组为什么反而最高

A 组 112 条全对，而三档"正规做法"都做不到。是不是说明手写 JSON 更好？

**不能这么读。** 三个理由：

1. **A 组的 prompt 是调出来的**。那 13 个例子是一轮轮针对这 112 条补的，其中包括 10-17 专门为 delete 反问补的那一例。B 组从零开始，两者不在同一起跑线上。
2. **统计上判不出差异**。A 与各组之间的 p 值都在 0.248~1.000，最接近显著的也只有 24.8%——按惯例要 p<0.05 才能说"确实不同"。
3. **A 组的优势有明确代价**：需要自己写 `json.loads` + 容错解析（模型偶尔会在 JSON 前后加废话）、需要自己维护输出格式约定、`type` 字段完全无约束。B/C 组这一层是**服务端 schema 兜着的**。

公允的说法是：**在已经调优过的 prompt 上，手写 JSON 与 function calling 打平**；机制本身的优劣，这个小样本量还判不出来。

## 7. 成本：省下的解析，换来了 token

工具表是**每次请求都随 body 发**的固定开销：

```
TOOLS_SCHEMA：10 个工具，2303 字符 ≈ 1151 token
B1 prompt：1068 字符
B2 prompt：  946 字符
```

也就是说，function calling 用**约等同于 prompt 本身大小的固定 token**，换掉了手写解析。

延迟实测（各 3 次，同一输入）：

| 组 | 耗时（ms） |
|---|---|
| A_手写 | 1074 / 906 / 988 |
| B1_原生 tools | 976 / 824 / 593 |
| C1_langchain | 745 / 902 / 936 |

**这三档没有可分辨的差异**——波动幅度（A 组自己就差了 168ms）比组间差异还大。网络往返占绝对主导，框架那点封装开销淹在里面了。

> 想看真实 token 消耗，得在 `run_compare.py` 里记 `response.usage`。本轮结果文件没记，所以上面只有工具表的静态估算。

## 8. 泛化验证：换一份没见过的 57 条，结论还站得住吗

第 4.4 节说过：**继续针对这 112 条调 prompt 已经没意义了**。这句话必须被验证，否则它只是一句自我安慰。

于是另造了一份验收集 `bench/holdout_set.json`，**57 条**，规则如下：

- **写标准答案时没有跑过任何模型**。标答先定稿，跑完不管多难看，一个字都不改
- 与老集**逐字不重复**、内部不重复；6 字连续撞车只有 1 处（`一下，我的车`），是自然用词而非句式模仿
- 结构完全同构：只有 `text / type / tool` 或加 `args` 四种键，**没有备注字段**（备注会成为调 prompt 时的素材来源，等于提前泄露标注意图）
- 参数样本把 `lineno` 扩到 **5 / 6**（老集只到 4），考"遇到没见过的序号敢不敢猜"
- 配比：42 command / 15 chat，chat 占 26%，比老集的 17% 更高——边界样本全在 chat 这一侧

### 8.1 结果

| 组 | 分流 | 完整 | 参数 |
|---|---|---|---|
| A_手写 | 98.25% | **96.49%** | 12/12 |
| B1_照搬 | 98.25% | 94.74% | 12/12 |
| B2_配平 | 96.49% | 91.23% | **10/12** |
| C1_lc 照搬 | 98.25% | 94.74% | 12/12 |
| C2_lc 配平 | 96.49% | 91.23% | **9/12** |

### 8.2 复现的：LangChain 零损耗，而且复现了两次

```
B1 vs C1:  b=0 c=0，三元组逐条全同
B2 vs C2:  b=0 c=0，三元组逐条全同
```

第一次在 112 条上，这次在**从没见过的 57 条**上。而且这次是**两条独立路径**（JSON 语境 prompt 一组、中立 prompt 一组）同时零差异。

这排除了"112 条上碰巧相等"的可能。**LangChain 不引入正确性损耗，这件事现在有跨数据集证据。**

### 8.3 没有复现的：B2 的配平优势，换数据就消失了

```
112 条：  B1 97.32%  →  B2 99.11%    ← 配平"有效"
 57 条：  B1 94.74%  →  B2 91.23%    ← 配平"反而更差"
```

方向反了。`A vs B2`：b=3, p=0.248（仍然不显著），但趋势是明确的，而且 B2 和 C2 两条独立路径**同时**下滑。

这说明：**第 4.3 节那个"修好开会、快递 2 条"的收益，是针对这 112 条调出来的，不是普适能力提升。**

### 8.4 新增的失败，根因还是那条老机理

B2/C2 在新集上共同多出 3 条失败，全在"删除"边界上：

| 输入 | 期望 | B2 / C2 实际 |
|---|---|---|
| 第二条备忘不需要了 | delete_memo | list_memos |
| 帮我清掉待办第二条 | delete_todo | list_todos |
| 把第六条待办划掉 | delete_todo | list_todos |

三个都退化成"先查列表"，没敢直接删。

看 B1 prompt 的原话：

```
删除类工具二选一：用户给了明确序号 → {"lineno": 3}；描述内容特征 → {"keyword": "开会"}
```

我在 B2 里译成「用序号 / 用关键词」。**"删除类工具"这个标签被换掉的同时，"删除"这个动作语义也丢了一半**——模型看到"第二条备忘不需要了"，只知道有个编号，不知道要删，所以先 `list_memos` 看一眼。

这和 112 条上「把 `complete_todo` 译成中文导致提示变弱」是**同一个机理的第二次独立复现**。两条独立证据摆在一起，这个结论可以当作稳定的：

> **翻译 prompt 时删掉的"格式词"，往往同时带走了"语义词"。去 JSON 化不是无损压缩。**

### 8.5 一条被确认的硬边界

`我的生日是四月八号` → **五组全判 `add_memo`**（应判 chat）。

当初写这条就是为了验：112 条上那条"女朋友生日"到底是个例还是普遍规律。答案是**普遍**——换主语、换日期，五组全错。

第 4.4 节那句"这个边界不是 prompt 能修的"，现在有了跨数据集的支撑。

### 8.6 新集暴露的两条老集没考到的问题

| 输入 | 问题 |
|---|---|
| 记一下大后天上午九点去车管所换证 | B1/C1 判 `add_memo`（A 组对）。"大后天"这么强的时间信号没被抓到 |
| 帮我查下这几天的天气 | B2/C2 判 `chat`。天气查询被当成闲聊 |

这两条在 112 条里没有同类样本，属于**覆盖盲区**，不是本次实验造成的。

### 8.7 口径

新集所有对比的 **p 值都在 0.248 ~ 1.000**，统计上依然判不出显著差异。57 条这个体量，3 条差异到不了 p<0.05。

能说的是**趋势变了**，不是"显著变差"。但趋势的一致性（B2/C2 双路径同向、多条失败同机理）比单个 p 值更有说服力。

## 9. 局限与自我批评

诚实列在这里，写报告不能只挑好看的说。

**① temperature=0 不等于确定**
B2 的**参数命中在两次跑批之间从 26/27 变成了 27/27**（昨天错的那条 `帮我把上回记的门禁密码那条删了` 今天对了）。

所以 C2 的 26/27 **不能**拿来跟 B2 的 27/27 比——两次失手的根本不是同一条样本。这一对合计只有 1 条差异，p=1.000。

本轮唯一能硬说的话是：**B1 与 C1 的零差异**。其余差距一律只能写"无显著差异"。

**② 样本量小，只能证伪不能证实**
112 条、27 个带参数样本。3 条差异的 p 值就在 0.25 左右——这个体量筛不出 3 个百分点以内的差别。

**③ prompt 是我改的，存在主观性**
B2/C2 那份中立 prompt 是我写的，其中「记东西用哪个工具」整段其实是"补充翻译"（A 组靠例子承载、B 组没例子可用），不是"等价翻译"。写报告时必须把这两类改动分开，不能全算成"配平"。

**④ 有一处我曾污染测试数据**
B2 第一版我把「我女朋友的生日是三月十二号」的**原句**抄进了 prompt 当反例。已删除。但这本身是个教训：**对着测试集改 prompt，很容易不知不觉把答案写进去**。

**⑤ 评测口径有盲区**
见第 5 节——`[工具结果]` 这条路径完全没被覆盖。

**⑥ 57 条新集也有它自己的局限**
- **它是我造的，不是外部数据**。虽然写标答时没跑模型，但句式选择仍受我的判断影响
- **只有 57 条**，比 112 条更小，p 值更压不下来
- **它现在也不能再用于调 prompt 了**。跑过一次，就变成"看过结果的数据"。真要再验，得再造第三份
- 老集上的 `酱油用完了`、新集上的 `第二条备忘不需要了` 这类边界，都可能只是**同一个覆盖缺口的不同表现**，而不是三个独立问题

**⑦ 一次跑批 = 一次快照**
两个数据集都是单次跑批的结果，没有做重复跑批取均值。按第 ① 条的漂移情况，单次结果里可能有 1~2 条是运气。

## 10. 结论

**框架层面**

1. **LangChain 正确性零损耗，有两个数据集的逐条证据**（112 条与 57 条上 `B1 vs C1`、`B2 vs C2` 均 b=0 c=0，三元组全同）。用不用它，是工程选择，不是准确率选择。

**prompt 与机制的关系**

2. **例子在 tools 模式下会毒化输出**——模型模仿形式优先于服从指令。这是必须删例子的硬理由。
3. **去 JSON 化会连带删掉承载语义的片段**。这条在 112 条和 57 条上**各出现一次、机理相同**：删掉 `complete_todo` 工具名 → 提示变弱；删掉"删除类工具"标签 → "删"的动作语义丢了。**prompt 与机制的耦合不止在输出格式，还在"怎么描述工具"这一层。**
4. **分数差距来自 prompt 与机制的匹配，但这个"匹配"是数据集特定的**。B2 在 112 条上 +2 条，在 57 条上 −3 条——对着一个验证集调出来的 prompt 收益，不保证能带到新数据上。

**机制本身**

5. **原生 function calling 有一段答话通道是裸的**。schema 只覆盖调工具那条路，`content` 无人约束。要么补 `text` 字段，要么走标准的两段式（`role='tool'`）。
6. **A 组的高分不等于手写 JSON 更优**。它在两个数据集上都是最高（100% / 96.49%），但都与各组无显著差异，且领先的是被针对性调优过的 prompt。

**边界**

7. **`陈述句 + 事实内容` 会被误判成"要记"**，且跨数据集稳定（女朋友生日、我的生日，五组全错）。这不是 prompt 能修的边界，需要机制或产品层面的处理（比如二次确认）。

---

## 11. 下一步

这次实验最有价值的东西，不是那五组分数，而是下面这条工作方法的印证：

> **任何"调完之后变好了"的结论，都必须换一份没见过的数据再说一遍。**
> B2 在 112 条上是唯一接近满分的对照组，换到 57 条上掉头向下——如果没造这份新集，报告里就会写下一个错的结论。

所以接下来：

- **不要再用这两份数据调 prompt**。它们都已经被"看过"了
- 真要继续优化，需要**第三份**独立数据，或者换一个真正的外部来源
- 剩下的功能项（语音接口、部署）与本次实验解耦，可以并行推进
