# 语音链路踩坑记录

> 从 `README.md` 的「开发中的实测记录」拆出来的一节。
> 语音是这个项目的**附加入口**（第一个入口是浏览器，第二个是键盘），
> 这些坑只在跑 `voice_cli.py` 时才会遇到，所以单独归档，不占主 README 的篇幅。

## 延迟怎么测才准

对应 `bench/run_latency.py`。

- **手测一次 = 只有一个数，分不清测的是哪一段**。旧版把一轮记成 9.5 秒，实测 12.6 秒 —— 漏的是 **TTS 播放时长**：`speak()` 里 `sd.play` 之后还有 `sd.wait()`，要等音频放完才返回
- **播放多久不是你定的，是音频长度定的**：句子越长播得越久。这台机器上"合成 0.71 秒 + 播放 2.83 秒"是**串行**的，两段合起来占了链路的一半
- **跑基准要把 `sd.play` 打桩掉**（`mock.patch('sounddevice.play')`），否则 20 轮会一直出声；但 `sd.wait` 的打桩**必须和录音测量分开作用域** —— `asr.record()` 内部也靠 `sd.wait()` 等录音结束，同一个 patch 里测录音会让它瞬间返回、数字全变成 0
- **别只看中位数**：同一环节的"最快"和"最慢"能差一倍以上，只报一个平均值会把偶发卡顿藏起来。旧版用联网合成时，端到端 10 轮曾出现最快 3.81 秒 / 最慢 14.77 秒（慢的全来自网络波动）；换本地合成后收窄到 2.20 ~ 3.02 秒
- 每个环节先跑 1 轮 **warmup 不计入**，否则"首次建连"的开销会把最慢值拉高

## `sounddevice` 录音

- `sd.rec()` 内部是 `np.empty((frames, channels))`，**永远返回二维** `(48000, 1)`，而 whisper 只吃一维。用 `.squeeze()` 或 `[:, 0]` 压维
  - ⛔ 别用 `reshape(-1)` / `flatten()`：单声道没事，但**双声道时会把左右声道交错拼成一条队**，不报错、数据是坏的
- `frames` 是**采样点个数**不是秒数（3 秒 = `3 * 16000`），且**必须是整数**
- `sd.rec()` 是**立刻返回**的。录音真正开始于它内部的 `stream.start()`，读取数据必须等 `sd.wait()`
  - 实测：`sd.rec` 这一行耗时约 99ms 才返回，此刻录进 **0** 个采样点；`sd.wait()` 返回时（约 3.09 秒）才是 48000/48000 满
  - 顺序是**反的**：录音先结束（录满了触发 `CallbackAbort`），`sd.wait()` 只是守着等结束通知
  - 不传 `out=` 时内部数组来自 `np.empty`（未初始化）。实测前几个值是 `-1.17e+35` 这种垃圾值 —— **不等 `sd.wait()` 就用，拿到的不是静音，是垃圾**

## `faster-whisper`

- `transcribe()` 返回的是 `(segments, info)` **两件东西**，且 `segments` 是**生成器**：`len()` 报 `TypeError`、下标报 `TypeError`，**必须遍历**才吐内容，文字在 `seg.text`
- 生成器**只能走一遍**：第二次遍历得到空结果。`transcribe()` 本身几乎瞬时返回（0.01s），真实耗时（约 1.5 秒）发生在遍历时
- 必须传 `initial_prompt='以下是普通话的句子。'` —— 不加会输出**繁体**
- 模型**不能用 `base`**：base 压不住，中文会吐繁体，必须 `small` 及以上
- 静音输入（全零、各种底噪）稳定返回空字符串，**没有幻觉输出**

## `sherpa-onnx` 本地 TTS（以及为什么不再用 edge-tts）

- edge-tts 要联网（`speech.platform.bing.com`），网络一断 TTS 直接失败 —— 这是换本地的直接原因。本地合成不联网、快约 3 倍
- **配置是三层套娃**：`OfflineTtsVitsModelConfig`（装 4 个模型文件路径）→ 塞进 `OfflineTtsModelConfig(vits=…)` → 再塞进 `OfflineTtsConfig(model=…)` → 最后交给 `OfflineTts(配置)` 得到引擎。引擎建在**模块级**（加载要 0.6 秒，别每句话重来）
- ⛔ **四个路径只能传 `str`**：传 `pathlib.Path` 会报 `TypeError: incompatible constructor arguments` —— 报错一个字都不提"路径"，极难查。都要 `str(...)` 包一层
- `generate(text, sid=2, speed=1.0)` → 拿 `.samples`（⚠️ **是 list，不是 ndarray**，得先 `np.asarray`）和 `.sample_rate`（**16000**，与 ASR 天然对齐，不用重采样）
- ⚠️ **合成长度每次不同**（模型内部时长预测带随机性），头尾的静音也在 **0~150ms 之间乱跳**（有时是 0 → 听感"戛然而止"）。所以**必须自己补固定静音**：头 0.1 秒 + 尾 0.3 秒。⛔ `time.sleep()` 没用（那只让程序等，不改音频）
- ⚠️ **输出峰值只有 0.2~0.35**，直接播偏轻 → 归一化：`s / np.abs(s).max() * 0.9`。注意是 `np.abs(...).max()` 而不是 `max(...)`（后者取带符号最大值，负半边更深时会冲出 1.0，`max()` 这个错还是**间歇性**的，随手试一句可能正好正常）
- 🔴 **字表读不出的字符会被"静默跳过"**（`lexicon.txt` 里没有阿拉伯数字，`tokens.txt` 里标点只认 `，。！？—…`）→「第3条」播出来变「第条」。修法是**送进 TTS 前做文本清洗**（数字转中文 + 标点归一 + 白名单过滤），而不是去改模型文件（改 `tokens.txt` 会让合成直接崩，改 `lexicon.txt` 只能枚举、覆盖不了任意数字）

## 实测性能

| 环节 | 耗时 |
|---|---|
| ASR（faster-whisper small，本地） | ≈ 1.5 秒 |
| 路由 + 工具（DeepSeek） | ≈ 0.6~1.1 秒 |
| TTS 合成（sherpa-onnx，本地） | ≈ 0.71 秒 |
| TTS 播放 | ≈ 音频长度（2~3 秒） |
| **端到端一轮** | **≈ 8.7 秒** |

播放在总耗时里占大头，且不可压缩 —— 想快只能做流式（边合成边播）。
