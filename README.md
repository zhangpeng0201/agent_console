# Agent 控制台

一个**说一句话就能用**的 LLM Agent：浏览器或语音输入 → 意图路由 → 调用工具 / 闲聊 → 返回结果。

重点不在"能聊天"，而在**把一句话准确地分派给正确的动作**。为此做了一套可复现的评测（112 条单轮 + 25 轮多轮），并用**同模型、同 prompt、同 112 条样本**的对照实验，把「结构化输出该怎么拿」拆成可量化的三层：手写 JSON、原生 function calling、LangChain。语音与键盘都只是入口，共用同一个内核。

> **在线体验**：<https://zhangpeng0201-agent-console.ms.show> —— 打开即用，不用登录、不用装环境（免费实例久无访问会休眠，首次打开需等几十秒唤醒）
>
> **速览**：10 个工具 · ReAct 循环 · 多轮会话（会话与数据归属分离）· 112 条单轮评测 + 25 轮多轮集 · 框架对照实验（2×2 因子）· 语音全离线
>
> 更新：2026-10-19

## 功能

| 你说 | 它做什么 |
|---|---|
| 帮我记一下房门密码是1234 | 存入备忘录 |
| 记一下明天下午三点开会 | 加入待办 |
| 我都有哪些备忘 | 列出已存的备忘录 |
| 待办有哪些 | 列出未完成的待办 |
| 删除备忘第三条 | 删掉备忘录里第 3 条 |
| 待办第三条已完成 | 把第 3 条待办标记为已完成 |
| 现在几点了 / 今天星期几 | 读本机时钟并回答 |
| 北京今天天气怎么样 | 查天气（高德 API），播报实况 + 未来三天 |
| 帮我搜一下最近的 AI 新闻 | 联网搜索（博查 API），返回摘要 |
| 先记一下明天开会，再提醒我晚上打电话 | 一句话两件事：连续调两个工具（ReAct 循环） |
| 今天好累啊 | 闲聊回应（不调用任何工具） |
| 退出 | 结束程序（键盘版输入 `quit` 或 `q`） |

> 「第三条」指的是**列表里显示出来的行号**（从 1 开始），不是记录内部的 id。行号删完一条会自动重新连续。

三个入口，共用同一套内核 —— **浏览器是主入口，键盘第二，语音第三**：

| 入口 | 启动方式 |
|---|---|
| **浏览器**（主） | `cd src && uvicorn api:app --port 8000` → 打开 <http://127.0.0.1:8000/> |
| 键盘 | `cd src && python cli.py` |
| 语音 | `cd src && python voice_cli.py`（说话 → 识别 → 回复语音播报，同一套业务逻辑） |

线上跑的就是浏览器入口：<https://zhangpeng0201-agent-console.ms.show>

## 快速开始

三条路，按需要挑一条。

### A. 在线体验（0 安装）

<https://zhangpeng0201-agent-console.ms.show> —— 浏览器直接打开，不用装任何东西。免费实例长时间无访问会休眠，首次打开可能要等几十秒唤醒。

### B. 本地跑 Web 版（约 1 分钟，不需要语音模型）

**1. 只装 6 个包**（等价于 `pip install -r deploy/requirements.txt`）

```bash
pip install fastapi==0.143.2 uvicorn==0.54.0 openai==3.23.0 requests==2.34.2 python-dotenv==1.2.4 tzdata==2026.5
```

**2. 配 key** —— 项目根建 `.env`

```ini
DEEPSEEK_API_KEY=你的key
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

**3. 启动**

```bash
cd src
uvicorn api:app --reload --port 8000
```

浏览器打开 <http://127.0.0.1:8000/>。

⚠️ **必须在 `src/` 目录下运行**。项目用裸 import（`from handle import handle`），没有 `src.xxx` 前缀，也没有 `__init__.py`。在 PyCharm 里跑会自动把项目根加进路径，看起来能跑，但命令行会 `ModuleNotFoundError` —— 请以命令行结果为准。

### C. 本地跑命令行与语音版（需额外 118 MB 模型）

**1. 装全量依赖**（含语音链）

```bash
conda create -n voice_assistant python=3.11
conda activate voice_assistant
pip install -r requirements.txt
```

**2. 下载语音模型**（只跑键盘版可跳过）

语音链路的三个模型全部**在本机跑**，不联网：

| 用途 | 模型 | 位置 | 怎么来 |
|---|---|---|---|
| 语音识别 ASR | `faster-whisper` `small` | HuggingFace 本地缓存 | 首次运行自动下载（约 972 MB） |
| 语音合成 TTS | `sherpa-onnx-vits-zh-ll`（VITS，5 个音色） | `model/sherpa-onnx-vits-zh-ll/` | **手动下载** |
| 静音检测 VAD | `silero_vad.onnx`（约 2.2 MB） | `model/silero-vad/` | **手动下载** |

`model/` 目录**不进 git**（TTS 模型约 116 MB）。要跑语音链路，按下面的结构把两个模型放到位：

```
model/
├── sherpa-onnx-vits-zh-ll/       # 语音合成（VITS）
│   ├── model.onnx                # 约 116 MB
│   ├── lexicon.txt
│   ├── tokens.txt
│   └── dict/
└── silero-vad/
    └── silero_vad.onnx           # 约 2.2 MB
```

- **TTS 模型**：sherpa-onnx 官方发布的 `sherpa-onnx-vits-zh-ll`（仓库 `k2-fsa/sherpa-onnx` 的 tts-models 发布页）
- **VAD 模型**：Silero VAD v5 的 ONNX 导出（2,327,524 字节）

ASR 与 TTS 的模型都在**进程启动时加载一次**（`voice_cli.py` 一启动会先看到"正在加载语音识别模型 / 语音模型已就绪"，约 2 秒），之后整个进程复用 —— 不会每说一句话就重新加载。

**3. 运行**

```bash
cd src
python cli.py        # 键盘版（不需要语音模型）
python voice_cli.py  # 语音版（需上面的模型）
```

> 语音链路的踩坑（录音、ASR、TTS）见 [docs/语音链路踩坑记录.md](docs/语音链路踩坑记录.md)

### 依赖分层

| 层 | 装什么 |

## 部署

线上地址：<https://zhangpeng0201-agent-console.ms.show>

`deploy/` 是部署专用的裁剪副本：只保留 Web 服务需要的文件，语音链（`faster-whisper` / `sherpa-onnx` / `sounddevice`）和离线基线全部去掉，依赖从 55 行收敛到 6 行。

```
deploy/
├── Dockerfile          # python:3.11-slim + 6 个依赖 + src/
├── requirements.txt    # 6 行，空 venv 实测可用
├── ms_deploy.json      # 魔搭部署声明（docker / 2v-cpu-16g-mem / port 7860）
└── src/                # 从 src/ 同步的副本（不含语音相关文件）
```

三处关键决策：

| 决策 | 原因 |
|---|---|
| 用 `--app-dir src` 而不是 `cd src` | `tools.py` 的 `BASE_DIR = Path(__file__).resolve().parent.parent` 依赖 cwd；切目录后数据会落到 `/app/src/output` |
| `COPY requirements.txt` 排在 `COPY src/` 之前 | 分层缓存：只改代码时不必重装依赖 |
| 依赖里必须有 `tzdata` | slim 镜像没有 `/usr/share/zoneinfo`；缺了不是启动崩，而是**第一次调时间工具**时抛 `ZoneInfoNotFoundError` |

改完 `src/` 后重新部署：

```bash
robocopy src deploy/src /MIR /XD __pycache__ /NFL /NDL /NJH /NJS
```

然后把 `deploy` **整个文件夹**上传到魔搭创空间 → 在「设置 → 环境变量」填 10 个 key → 点部署。

> 环境变量只能填在平台设置里：`sdk_type: docker` 时 `ms_deploy.json` 的 `environment_variables` 字段不生效。顺序也不能反（先配 key 再部署），否则服务能起来、页面能打开，但一发消息就 500。

**已知限制**：容器重启后 `output/` 的数据和 `STORE` 里的会话全部清空（免费实例无持久卷）。

## 架构与数据流

```
   入口（只收输入、给输出）           内核（项目主体）                    输出
   ──────────────────────           ──────────────                    ────
   api.py        网页 ───文字──┐
   cli.py        键盘 ───文字──┼──→  handle()   分流核心
   voice_cli.py  语音 ───文字──┘         │
        │                               │  llm_router.route()  判断该做什么
        └─ asr.py                      ├─→ command → 调用工具 ─┐
           录音（VAD 断句）→ 转文字     └─→ chat    → 闲聊应答 ─┘
                                                               │
                                    ┌──────────────────────────┘
                                    ↓
                   ┌────────────────┼─────────────────┐
                   ↓                ↓                 ↓
           api 返回 JSON      cli 打印屏幕      tts.speak() → 喇叭
           （浏览器渲染）                        （仅语音入口）
```

分层规则（这是项目里最硬的一条约束）：

| 层 | 模块 | 职责 | 不允许 |
|---|---|---|---|
| 容器 | `schemas` | 定义数据形状 | — |
| 动作 | `tools` | 真正干活、读写文件 | 不认识路由 |
| 登记 | `registry` | 工具表 | — |
| 决策 | `llm_router` | 只判"该做什么"，不执行 | 不调用工具 |
| 编排 | `handle` | 把决策变成动作 | 不写业务逻辑 |
| 入口 | `api` / `cli` / `voice_cli` | 收输入、给输出 | 不写业务逻辑 |
| 搬运 | `asr` / `tts` | 声音 ↔ 文字 | **完全不碰业务逻辑** |

`asr.py` 和 `tts.py` 里没有 `handle` / `registry` 的任何 import，也不调用 `tools` 里的任何业务函数 —— 语音层只认识"声音和文字"这两个概念。（唯一从 `tools` 借的是 `BASE_DIR` 这个路径常量，用来定位 `model/` 目录，不涉及业务逻辑。）一旦语音层开始理解"意图""工具""备忘录"，分层就被污染了。

## 核心设计

### 1. 工具表是单一来源

`registry.py` 里一张表定义全部工具：

```python
{'name': 'add_todo', 'desc': '把用户将来要做的事情存入待办…', 'func': add_todo, 'args': ['text']}
```

这张表同时驱动三件事：

- 路由 prompt 里的工具清单（`llm_router` 自动拼装，不手写）
- 参数校验的白名单（多传参数拦、少传参数也拦）
- 执行时的函数查找（`handle` 按 `name` 查 `func`）

⚠️ **但"自动派生"只覆盖工具清单，不覆盖判断规则和示例**。prompt 里"什么时候该调哪个工具、参数怎么填"是靠**手写的规则和示例**教给模型的。所以加一个新工具要同步三处：`tools.py`（写函数）、`registry.py`（登记进表）、`llm_router.py`（prompt 里补规则和示例）。漏掉第三处，模型知道工具存在，却不知道何时调用它。

### 2. 三个入口共用一个内核

浏览器、键盘和麦克风走的是**同一个 `handle()`**。业务逻辑从入口里抽出来，每个入口只负责"收输入、给输出"：`cli.py` 打印到屏幕，`voice_cli.py` 多了录音和语音播报，`api.py` 把结果包成 JSON 并附带每一步的耗时。

### 3. 调用模型只有一个出口

所有模型调用都过 `llm_client.ask()`，参数集中在一处：

```python
{'model': 'deepseek-flash', 'max_tokens': 800, 'temperature': 0,
 'extra_body': {'thinking': {'type': 'disabled'}}}
```

`extra_body` 那行是**关掉模型的思考模式**。开着的时候，思考过程和正文共享 `max_tokens`，预算会被思考吃光、正文返回空字符串；而且思考模式下 `temperature` 不生效，结果不可复现。关掉之后：正文只占十几到二十几个 token、速度约快一倍、结果可复现。实测意图分类质量没有损失。

### 4. ReAct 循环：一句话可以连着调多个工具

早期版本**一次输入只做一次路由**：模型判出 `add_memo` 就执行、判出 `chat` 就闲聊，然后结束。所以「先记一下明天开会，再提醒我晚上打电话」这种一句话两件事，只能办成第一件。

现在 `handle()` 里套了一层 `while`（上限 `MAX_EPOCH = 5`）：

```python
decision = route(text, HISTORY)
while epoch <= MAX_EPOCH:
    ...
    reply = '【工具结果】：' + result
    decision = route(reply, HISTORY + messages)   # 把工具结果喂回去，看还要不要继续
    epoch += 1
```

- 每走一步，就把这一步的「模型决策 + 工具结果」追加进**本轮**的 `messages`，再连同历史一起问模型"这一步办完了，还要不要继续"
- 终止条件有两个：模型判 `chat`（闲聊应答）或判 `answer`（一句话收尾 —— 这是为循环新增的类型）
- ⚠️ **本轮 `messages` 是临时的**：工具结果**一个字都不进 `HISTORY`**，这一步走完就丢。否则工具返回的原文会在后续每一轮里反复出现，把模型带偏
- 实测：一句话两件事的样本能连续走两步（工具 A → 工具 B → `answer`），单发路由时代做不到

### 5. 多轮会话：两份历史

多轮要解决的是"助手记得上一句说什么"。这里没有用一套历史打天下，而是**两份**：

| 历史 | 存什么 | 喂给谁 | 为什么分开 |
|---|---|---|---|
| `HISTORY` | 模型的**决策 JSON** | `route()` | 让模型知道"上一句我判成了哪个工具、参数是什么"，才接得住追问 |
| `CHAT_HISTORY` | **人话**（用户原话 + 回复原文） | `chat()` | 闲聊只看人话；JSON 混进去会被当成"要模仿的格式" |

⚠️ `CHAT_HISTORY` 里**绝不能出现带 JSON 的历史** —— 实测模型会照着 JSON 格式胡说。这也是 `chat.py` 不复用路由那套 prompt 拼装的原因。

几条实现上的硬约束：

- `HISTORY` 里 assistant 那条是**两段**：决策 JSON + 换行 + `（已回复用户：X）` —— 后面那段告诉模型"这一句实际答了什么"
- 裁剪上限 `HISTORY_LIMIT = 20`，用 `del HISTORY[:-20]` 掐头。⚠️ **这个数必须是偶数**：一份历史是「用户 + 助手」两行一轮，取奇数会把一轮切成两半
- **候选换算（`PENDING`）**：上一轮刚列出一份候选（"你有这些待办：…"），用户这一轮说「第 3 条」—— 这个 3 指的是**候选列表里的第 3 项**，不是全局行号。所以每轮末尾记下 `PENDING = {'tool': ..., 'linenos': [...]}`，下一轮命中就按 `linenos[n-1]` 换成真实行号；换算不出来时置 `0`，让工具回"没有该记录" —— **宁可答错，也不误删**
- 四行 append（两份历史各两行）写在 `if / elif` **外面**，保证任何分支（含"没找到工具"）都进历史

### 6. 语音层（附加）：文本清洗 + 失败保险

`tts.speak()` 返回 `bool`，失败不抛异常；合成前还会先把文本「洗干净」：

- **读不出的字符先换掉**：本地模型的字表里没有阿拉伯数字，也没有 `：` `[]` `“”` 这类符号。直接送进去会被**静默跳过**（终端会刷 `Ignore OOV` 日志），「第3条」播出来变成「第条」。所以合成前：先把数字转成中文读法（`71 → 七十一`、`12345 → 一万二千三百四十五`），再把标点归一化，最后用**白名单**把剩下读不出的字符（英文、emoji……）一并删掉。⚠️ 屏幕上 `print` 的仍是原文，只清洗送进 TTS 的那一份
- **清洗后为空就直接返回 `False`** —— 否则空串会合成出 0 个样本，后面取峰值时抛异常
- 「合成 → 补头尾静音 → 归一化 → 播放」整段包在 `try` 里，出错打一条 stderr 警告并返回 `False`
- 降级策略由调用方（`voice_cli`）决定：播报失败就把回复文字打到屏幕上

`voice_cli` 里还有三道闸门，都是实测之后加的：

| 闸门 | 为什么 |
|---|---|
| 识别结果为空 → 提示"没听清"，直接下一轮 | 空字符串会被 `handle` 当成闲聊，白白说一句俏皮话，多花约 3 秒 |
| 命中退出词 → `break` | `handle` 只把"退出"当闲聊，不拦的话用户说了退出程序还在听 |
| `speak` 返回 `False` → 打文字兜底 | 此时工具已经执行完了（可能已经写进文件），不能重试，只能往"退"的方向降级 |

### 7. VAD 自动断句

早期版本录音是**固定录 5 秒**：说 1.5 秒也得干等到 5 秒满，说超过 5 秒则被截断。

改成逐帧判定的 VAD（Silero，走 `sherpa-onnx` 提供的接口）：录进来的音频每 **36ms** 切一帧，交给 `VAD.is_speech(帧)` 问"这一格里有没有人说话"。这个判定**自带滞回**，模型内置了两个时间常数：

| 内置参数 | 值 | 作用 |
|---|---|---|
| `min_speech_duration` | 0.25 秒 | **起始门槛**：累计 0.25 秒人声才算"开口"，敲键盘/碰桌子的瞬时噪声不触发 |
| `min_silence_duration` | **0.8 秒** | **判停**：连续 0.8 秒静音才认"说完了"，句中自然停顿不会把一句话切断 |

于是"说完了没"变成一个**状态跳变**：`is_speech` 从 `True` 变 `False` 的那一刻就是停录时机。真正要写的只剩一个流式录音循环 + 两种兜底（**最长 15 秒**强制停 / **一直没人说话 5 秒**放弃、返回空数组）。

⚠️ `min_silence_duration` 默认是 **0.5**，实测扛不住 0.6 秒的句中停顿：说「记一下」停 0.6 秒再说「明天下午三点开会」，会被切断、只录到前半句（半句话送进 `handle()` 可能执行错动作）—— 所以调成了 **0.8**，代价是每句话说完多等 0.3 秒。

## 评测结果

两套评测集，分开跑、分开报：

| 评测集 | 规模 | 跑法 | 看什么 |
|---|---|---|---|
| `bench/golden_set.json` | **112 条**单轮 | `run_eval.py` | 一句话分派对不对 |
| `bench/multiturn_set.json` | **12 段对话 / 25 轮** | `run_multiturn.py` | 带上下文时接不接得住 |

**单轮评测集**按加入时间分三段，覆盖 10 个工具 + 闲聊：

- **前 30 条**：最初版本，一字未动，覆盖 `add_memo` / `add_todo` / `list_memos` / `list_todos` / `chat`
- **第 31~66 条**：2026-10-08 扩充，新增 `delete_memo` / `delete_todo` / `complete_todo`
- **第 67~112 条**：后续补充，覆盖 `get_current_time` / `get_weather` / `web_search`，以及相对时间词、多动作、省略式指代等难例

其中 19 条是闲聊（期望不调任何工具），其余 93 条各对应一个工具调用。

**判卷口径**：三层指标 —— **分流准确率**（是"指令"还是"闲聊"）、**完整准确率**（分流 + 工具都对）、**参数准确率**（该传的参数抽对了没有）。

参数准确率**只对 27 条有唯一答案的样本生效**：`delete_memo` / `delete_todo` / `complete_todo` 收的是整数序号（"第三条" → `3`），对错能一锤定音；而 `add_memo` / `add_todo` 的参数是自由文本（`房门密码是1234` 与 `房门密码1234` 都不好算唯一答案）、查询与闲聊本来就无参 —— 这三类不进参数统计。**所以参数准确率的分母是 27，不是 112。**

### 主线路由（112 条）

`llm_router` 是把工具说明写进 prompt、要求模型输出 JSON、再解析的写法：

| 指标 | 结果 |
|---|---|
| 分流准确率 | **100.00%**（112/112） |
| 完整准确率 | **100.00%**（112/112） |
| 参数准确率 | **100.00%**（27/27） |

**多轮集（12 段 / 25 轮）同样 25/25。** 这套数字是回归基线：**改 prompt、加工具、动 `handle()` 之后必须整卷重跑**，任何一条掉下来都要先查清是代码问题还是抖动。

### 结构化输出：三种拿法的对照实验

同一个模型、同一批 112 条、同一份工具说明，只换「结构化输出从哪来」。

实验拆了两个变量 —— **机制**（prompt 里约定 vs 服务端 schema）和 **prompt**（JSON 语境 vs 机制中立）：

|  | JSON 语境 prompt | 机制中立 prompt |
|---|---|---|
| 手写 client（`response_format=json_object`） | **A**（主线） | —— |
| 原生 `tools=`（手写 client 传 schema） | **B1** | **B2** |
| LangChain `bind_tools` | **C1** | **C2** |

两张 prompt 在 B/C 之间**是同一个对象**（`import` 复用，不是复制），保证 2×2 里 prompt 这个变量一字不差。

| 组 | 分流 | 完整 | 参数 |
|---|---|---|---|
| A_手写 | 100.00% | **100.00%** | 27/27 |
| B1_照搬 prompt | 99.11% | 97.32% | 27/27 |
| B2_配平 prompt | 99.11% | **99.11%** | 27/27 |
| C1_lc 照搬 | 99.11% | 97.32% | 27/27 |
| C2_lc 配平 | 99.11% | 98.21% | 26/27 |

**三条结论**：

1. **LangChain 零损耗**。`B1 vs C1`：b=0 c=0，112 条逐条比对 `分流/工具/参数` 三元组**全同，0 条不同**——连错的地方都一样。换框架不引入正确性风险，选不选它属于工程取舍。
2. **缺口全部来自 prompt 与机制的匹配**。B 组相对 A 组掉的 3 条，方向高度集中（全部偏成 `add_memo`），根因是 tools 模式下**必须删掉 prompt 里的 JSON 示例**——而示例原本同时承担了"教格式"和"教边界"两件事。反过来，照抄旧 prompt 会让模型**用文本模仿示例**而不是填 `tool_calls`（实测 delete 类样本 0/18，删掉示例后 18/18）。**例子 > 指令。**
3. **A 组的高分不等于手写 JSON 更优**。A 组的 prompt 是针对这 112 条一轮轮调出来的，B/C 从零开始，不在同一起跑线；且 A 与各组之间的 McNemar p 值都在 0.248~1.000，**统计上判不出差异**。公允说法是：在已调优的 prompt 上，手写 JSON 与 function calling **打平**。

### 泛化验证：换一份没见过的数据，结论还站得住吗

上面 112 条已经被反复用来调 prompt 了，所以又造了一份 **57 条的验收集**（`bench/holdout_set.json`）——**写标准答案时没跑过任何模型**，跑完也不改标答。结果：

| 组 | 完整命中 | 参数 |
|---|---|---|
| A_手写 | **96.49%** | 12/12 |
| B1_照搬 | 94.74% | 12/12 |
| B2_配平 | 91.23% | 10/12 |
| C1_lc 照搬 | 94.74% | 12/12 |
| C2_lc 配平 | 91.23% | 9/12 |

**复现的**：`B1 vs C1` 与 `B2 vs C2` **都是 b=0 c=0**——LangChain 零损耗在两份互不重叠的数据上、两条独立路径上各复现一次。

**没复现的**：B2 的"配平优势"消失了，甚至反向（112 条上 97.32 → 99.11，57 条上 94.74 → 91.23）。方向性证据很明确：**对着一个验证集调出来的 prompt 收益，不保证能带到新数据上。**

**新增的失败根因还是同一条**：B2/C2 在"删除"边界上共错 3 条（`第二条备忘不需要了` → 退化成先查列表）。B1 的 prompt 写的是「**删除类工具**二选一：…→ `{"lineno": 3}`」，B2 译成「用序号 / 用关键词」，把"删除"这个动作语义丢了一半——和 112 条上"删掉 `complete_todo` 工具名导致提示变弱"是同一机理的第二次独立复现。

> 完整报告（含逐条失败分析、McNemar 全表、泛化验证专章、局限披露）：[`docs/框架对照实验报告.md`](docs/框架对照实验报告.md)

cd bench
python run_eval.py                    # 单轮：112 条

> 延迟基准默认**静音**（把播放打桩掉），并用本地合成的语音当"模拟麦克风输入"，所以跑起来不打扰人。跑 `handle()` 会真的写数据文件，脚本已经把数据目录指到临时目录、跑完即删。

## 实测性能

（开发机：Windows 11 / i9-13900HX / CPU 推理，无 CUDA）

**由 `bench/run_latency.py` 自动跑出**（每项 20 轮取中位数）。**键盘一轮是最短路径**，语音是附加入口、下面是它的成本明细：

| 环节 | 中位数 | 最快 | 最慢 | 说明 |
|---|---|---|---|---|
| **键盘一轮** | **约 0.7 ~ 1.5 秒** | — | — | 就是「路由 + 执行」那一行，**没有语音环节** |
| 路由 + 执行（指令） | **0.66 秒** | 0.36 | 0.95 | LLM 路由 + 工具调用，回复短 |
| 路由 + 执行（闲聊） | **1.52 秒** | 1.14 | 2.09 | 闲聊要生成整段回复，比指令慢一倍多 |
| —— 以下三行为**语音入口**（附加）才有的环节 —— | | | | |
| 录音（VAD 自动断句） | **约 2.9 秒** | — | — | 说 2.3 秒的话实测停录在 2.95 秒（老版固定录 5.11 秒） |
| ASR 语音识别 | **1.60 秒** | 1.51 | 1.67 | `small` 模型，`cpu_threads=8` |
| TTS 合成 | **0.71 秒** | 0.58 | 0.80 | 本地 sherpa-onnx 合成 + 文本清洗 + 补静音 |
| TTS 播放 | **2.83 秒** | — | — | 等于音频时长，实时播放压不掉 |
| **语音一轮** | **约 8.7 秒** | — | — | 2.9 + 1.60 + 0.66 + 0.71 + 2.83 |
| ASR 模型加载 | 约 2 秒 | — | — | 整个进程只发生一次，不是每轮 |

> ⭐ **对比 2026-10-08（旧版边缘 TTS + 固定录音）**：语音一轮从 **12.6 秒** 降到 **约 8.7 秒**，省下 **约 3.9 秒**，来自两处 —— **录音 5.11 → 约 2.9 秒**（VAD 自动断句，不再死等 5 秒）和 **TTS 合成 2.11 → 0.71 秒**（本地合成，不再联网，快约 3 倍）。

> **「录音」这一栏的口径**：这次基准跑用 `--skip-record` **跳过了麦克风**（安静、不打扰），所以那一行不是脚本量出来的，而是单独实测的 —— 用一段 2.34 秒的语音喂进 `record_until_silence()`，实测停录在 **2.95 秒**（≈ 说话时长 + 0.6 秒离场延迟）。⚠️ 这个数**随说话长短浮动**，不是固定值 —— 这正是 VAD 的意义。

> **「播放」这一栏的口径**：播放时长**等于音频本身的长度**，句子越长播得越久，压不掉。这一栏和旧表的 3.41 秒**不可直接比**（两句的音频长度不同）。

TTS 的"合成 0.71 秒"和"播放 2.83 秒"是**串行**的 —— 合成完才开始播，这两段合起来仍占链路的一半。本地化把"合成"从 2.11 秒压到 0.71 秒，但"播放"受限于音频长度，动不了。

**语音识别的准确度**：对合成语音做了端到端测试，**意图命中 6/6**；但**字面准确率只有 82.8%（字错率 17.2%）**。

最典型的一条：whisper 把「**备忘**」听成了「**背望**」。如果按字面判分，这条是错的；但路由照样正确地把这句话分派给了 `list_memos`。

**这就是判分口径定成"意图命中"而不是"字面一致"的原因** —— 真实语音里同音字、标点、语气词的差异会一直存在，只要事情办对了，用户不会觉得助手坏了。

## 已知限制

- **横向对比的样本量偏小**：112 条、27 个带参数样本。3 条差异的 McNemar p 值就在 0.25 左右，这个体量筛不出 3 个百分点以内的差别
- **参数准确率暂时没有区分度**：能判参数的 27 条样本，主线全部抽对（27/27）。要压出差别，需要更绕的序号说法（"把倒数第二条删了"、"删掉最后记的那条"）
- **`temperature=0` 不等于确定**：同一条样本两次跑批可能给出不同判定（实测 `那个，我女朋友的生日是三月十二号` 稳定判错，但 B2 的参数命中在两次跑批间由 26/27 变成 27/27）。所以 1 条以内的差异不能当结论
- **答话通道没被评测覆盖**：`[工具结果] → 回答` 这条路径，单轮集不喂、多轮集的历史里也不含，所以现有分数是"这题没出"，不是"考过没扣分"
- **`那个，我女朋友的生日是三月十二号` 是已知硬边界**：换成 function calling 后四组全判 `add_memo`（应判闲聊）。试过在 prompt 里补规则甚至直接写反例，**仍然判错** —— 这个边界不是 prompt 能修的，得换机制或加二次确认
- **VAD 断句有两个边界**：中段超过 0.8 秒的停顿会被当成"说完了"，把一句话切成两半；说话短于 0.25 秒的极短应答（"嗯""哦"）会被判成"没人说话"而丢弃。这两个是 `min_speech_duration` / `min_silence_duration` 的取舍，想更灵敏就会更容易误切
- **工具集 10 个**：覆盖新增 / 查询 / 删除 / 标记完成，另有时间查询（`get_current_time`）、天气查询（`get_weather`）和联网搜索（`web_search`）。
- **Ctrl+C 在 PyCharm 的 Run 窗口里无效**：那个面板不转发信号。要在真正的终端里跑（PowerShell / CMD），或者勾上 `Run → Edit Configurations → Emulate terminal in output console`
- **未在 CUDA 上跑过**：语音识别和 TTS 都有 GPU 加速空间
